# Progress — 2026-10-14 (Fabric feasibility, repo reorganization, MultiLoader, Fabric build)

The question was what maintaining a Fabric build would take now that the fork
has drifted far from upstream Voxy. Answer: realistic on MC 1.21.1, because the
loader coupling is small. The user approved the plan and went to sleep,
asking for Phases 0 and 1 and the Fabric port on three stacked branches, each
with a draft PR, everything checkable verified without an in-game test.

## Fabric feasibility

- Only 11 of 230 Java files import `net.neoforged`. Rendering, storage, world
  engine and the Sodium/Iris/Lithium mixins are loader-agnostic (same classes
  on both loaders for a given version).
- Loader-bound pieces: `@Mod` entrypoint, 9 server event handlers in
  `VoxyServer`, networking registration in `VoxyNetworkHandler`, client chunk
  ingest, commands, `ModLoaderUtil`/`FMLLoader`/`ModList` calls, Chunky
  `MixinNeoForgeWorld`, Sodium 0.8 `@ConfigEntryPointForge`.
- No Fabric API event exists for `ScreenshotEvent` (F2 sidecar) nor
  `CustomizeGuiOverlayEvent.DebugText` (F3): both need mixins on Fabric.
- Client commands use `CommandSourceStack`; Fabric client commands use
  `FabricClientCommandSource`, so `VoxyCommands` must become generic.
- Upstream Voxy is on MC 26.2 with no 1.21.1 branch. Going back to it would
  lose server LOD streaming, SSAO, Chunky integration, RocksDB recovery, the
  off-thread bakery, 16px textures, the debug sidecar and many crash fixes.

## Phase 1 + 2 — MultiLoader layout, NeoForge only (`build/multiloader`)

  `neoforge/` (`VoxyNeoForge` entry point, `NeoForgeServerEvents`,

  `sodium8` source set, `neoforge.mods.toml`), `buildSrc/` conventions adapted
  from krios.
- Build: ModDevGradle 2.0.49-beta (NeoForm for `common`, NeoForge for
  `neoforge`), Shadow 8.1.1 for the bundled libraries. Architectury Loom is gone;
  no remapping step on NeoForge.
- Platform services (ADR-008): `commonImpl.platform.IPlatform` and `INetworking`
  via `ServiceLoader`; `ModLoaderUtil` kept as a facade. `VoxyServer`,

  `JordanOlivet/ci-workflows` `build-gradle-mod.yml` (push to `dev`, PRs, manual).

- Jar naming per ADR-009 (still `proposed`): `neo-voxy-neoforge-1.3.0.jar`.

## Gotchas (hard-won, Phase 1)

- An access transformer is applied before NeoForm recompiles Minecraft, unlike
  the widener applied to bytecode: overrides of a widened method must be widened
  too (`cutoutTexture` in `MultiTextureStateShard` and `TextureStateShard`),
  owner classes of widened members must be listed explicitly, and record fields
  are not widened at all (`PalettedContainer.Data`: use `palette()` /
  `storage()` accessors).
- Compiling `common` needs the Mixin of the loaders (Fabric's `sponge-mixin`
  0.15.x, for `order` on injectors) and MixinExtras 0.4.x (`@WrapMethod`).
- ModDevGradle in NeoForm mode does not put Minecraft's libraries on the test
  classpath: `addModdingDependenciesTo(sourceSets.test)`.
- Shadow 8.1.1 does not treat `exclude` patterns as task inputs: after changing
  them, `:neoforge:shadowJar --rerun`. A bundled library's
  `META-INF/versions/9/module-info.class` must be excluded (`**/module-info.class`).
- The dev server needs LWJGL core for the bundled lwjgl-lmdb/zstd modules (a
  dedicated server ships none): added to the server run only
  (`additionalRuntimeClasspathConfiguration`).
- Iris 1.8.0 does not apply on Sodium 0.6.13 (`MixinCloudRenderer`); dev runs
  use 1.8.12.
- Sodium 0.8.12 cannot run in dev at all (bootstrap jar and nested mod jar need
  separate layers).
- A dev client started while the Windows session is locked stays on the loading
  overlay; screen capture fails too. The mixin audit works regardless.
- Killing a game JVM whose stdout is redirected to a log file still being read
  by a new run mixes both outputs: one log file per run.

## Findings (Fabric)

- Sodium 0.8.12 Fabric is built with Loom 1.16.1, which Loom 1.8 refuses to
  remap, and so are recent Fabric API builds (0.116.x). Hence the Mojang-mapped
  compile path for `sodium8`, Fabric API 0.109.0 in dev, and no Sodium 0.8 dev
  run on Fabric. Upgrading Loom would also mean a newer Gradle (ADR-010).
- Loom adds `"refmap"` only to mixin configs of the Fabric project's own
  resources; the two shared configs get it injected by `processResources`
  (NeoForge keeps them without, to avoid a missing-refmap warning).
- Fabric runs the client entry point before `RenderSystem.initRenderer`, so
  `initVoxyClient()` runs once, from `MixinRenderSystem`. NeoForge runs it twice
  (the mixin, then client setup): this predates the port and was left as is.
- No Fabric equivalent of client-only dependencies: a dedicated Fabric server
  logs that the recommended Sodium is missing. Harmless.

Found, predates the port (same code on `dev`), not fixed:

## New LOD mod: state-of-the-art analysis (`docs/lod-engine-analysis`)

The user is considering a new, publishable LOD mod written from scratch
(Voxy's license forbids redistribution, and Neo-Voxy has drifted far from it).
Asked for an exhaustive analysis before a Q&A session; the three pre-existing
bugs above get their own PR afterwards.

- Wrote `docs/analysis/lod-engine-state-of-the-art.md`: legal constraints and
  a clean-room process, lessons from Neo-Voxy, ecosystem as of 2026-10,
  data model, storage, acquisition, meshing, rendering, shader packs,
  networking, JVM performance, architecture, candidate architectures, spikes,
  risks and the open questions.
- Sources read directly: Distant Horizons core (column data points, SQLite,
  compression modes, generation modes, pull protocol, `BLAZE_3D` rendering
  engine) and upstream Voxy (26.2, OpenGL 4.6 only, license), both cloned
  read-only outside the repo; Voxy PR #614 (Vulkan by adopting the game's
  `VkDevice`, closed unmerged); NeoForge 26.3 primer (Renderpearl).
- Key facts: Vulkan is the default graphics API since 26.4-snapshot-1;
  Renderpearl exposes no compute, storage buffers or multi-draw indirect
  (third-party table); Iris has no Vulkan support, Aperture is in development.
- Measured: `dev/server-neoforge/world/voxy` is 407 MB for 241 MB of region
  files (LOD data 1.7x the world).
- No decision taken: everything waits for the Q&A (section 18 of the doc).
- First user answers recorded in the doc (§1.1, §1.2): both 1.21.1 and 26.x
  from the start, private repository until presentable, Windows and Linux,
  no announced minimum hardware, zero-config shader packs as a goal, large
  servers, unexplored terrain shown coarsely, 256-512+ chunks, solo project
  without deadline. New requirements: a command that builds LOD for an
  already-generated world (throttled, run at night), and later a world map
  showing each chunk's LOD state and errors. Name ideas checked against
  Modrinth (§1.5). Licensing nuance: Neo-Voxy was never published and our
  own concepts are reusable; only copying code as is is excluded.

## Fix of the three pre-existing bugs (`fix/preexisting-session-ingest-bugs`)

- Stale server support: `VoxyNetworkHandler.resetConnectionState()` now runs
  in `MixinMinecraft` on every `Minecraft#disconnect` and in the
  `LodReceptionService` constructor (one per connection).
- Light race: `VoxelIngestService.enqueueIngest` tests
  `getDataLayerData(pos) != null` (sky or block) instead of
  `getDebugSectionType`. In 1.21.1 `getDataLayerData` reads
  `visibleSectionData` (volatile copy) and `queuedSections` (synchronized
  map); `getDebugSectionType` reads `sectionStates`, a plain
  `Long2ByteOpenHashMap` the light thread writes.
- Render statistics: both pages bind to `VoxyConfig.renderStatistics` and set
  the flag; `VoxyConfig.loadOrCreate` initialises `RenderStatistics.enabled`.
- Validated: `./gradlew build` green, 341 tests. Real NeoForge server with the
  fixed jar: Chunky pregenerated 441 new chunks, 490 `[VoxyIngest] ok`, zero
  `enqueueFalse`, zero errors (the new light check accepts lit chunks).
- In game (Fabric dev client, real `dev/server-fabric`), after the user freed
  the PC: joined the server with Voxy (server stream), restarted it without
  Voxy and reconnected in the same client session: `server lacks Voxy
  channel ... switching to client-local ingest` and `ClientChunkIngestListener
  active (mode=CLIENT_ONLY)`. Reverse direction too: Voxy restored, reconnect,
  server stream again. "Show Render Statistics" + Apply wrote
  `render_statistics: true`, the F3 HTC/HRS/VS/QC lines appeared, and after a
  client restart they were there without touching the option (reset to false
  afterwards).
- Seen on the way, cosmetic: on Fabric the Voxy F3 block is appended after the
  targeted-block lines, so it scrolls off screen while looking at a block.
